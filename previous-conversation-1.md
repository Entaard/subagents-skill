  ## Verification and root ownership

  The previous table’s “root plus optional worker” wording was misleading. Your proposed division is better for substantial tasks.

  Root must retain policy ownership of:

  - Declaring and accepting the baseline.
  - Granting the sole-writer lease.
  - Choosing acceptance criteria.
  - Accepting results and dispositioning findings.
  - Resolving conflicting evidence.
  - Revising the plan and making the completion claim.

  Root does not need to personally perform all the mechanical verification:

  - A Scout or Verifier can collect baseline hashes and build the reproduction.
  - A Verifier can run pre-implementation deterministic checks.
  - Blind acceptance-suite authors and pre-write critics should be independent workers.
  - The writer can run focused feedback checks, but meaningful acceptance and fix verification should normally be rerun independently.
  - Root should run only narrow settling commands where direct evidence is cheaper than another dispatch.

  Root should implement directly only when the mutation is small and tightly coupled, dispatch overhead exceeds the benefit, workers lack a required capability, or matching delegated failures have exhausted the retry ladder. A substantial
  implementation should normally have a dedicated Writer. The division of authority is in sage/skills/sage/references/codex.md:19, while the independent verification patterns are in sage/skills/sage/references/policy/topologies.md:13.

  ## Promotion selectivity

  Your concern is valid. Current Sage only partially solves knowledge bloat.

  Existing safeguards include:

  - Promotion is explicit and cannot run during an active Sage task.
  - Observations must become reusable decision rules, not merely outcomes.
  - Candidates require a qualifier, observable recognizer, falsifier, exact adopted-artifact provenance, and passing verification.
  - Candidates are refuted before landing.
  - Future runs list only lightweight index metadata and load only recognizer-matching records.

  These controls reduce automatic and runtime bloat. However, there is currently:

  - No minimum independent-run count.
  - No confidence or maturity score.
  - No maximum candidates per promotion batch.
  - No novelty or expected-utility requirement.
  - No measured activation/usefulness feedback.
  - No automatic protection against many narrowly different but overlapping rules.

  A single run can therefore support a promoted record. The implementation does not fully solve the problem; it relies on promotion judgment. See sage/skills/sage-promote/references/workflow.md:7 and sage/docs/phase0/promotion-contract.md:7.

  A better future gate would be evidence-class-sensitive rather than one universal count: allow a reproducible deterministic invariant from one run after independent refutation, require recurring empirical heuristics across several independent
  runs, and require stronger evidence plus behavioral evaluation before changing shared policy. A novelty/overlap test and batch-size budget would also directly address efficiency.

  ## Custom agents

  This is both a harness-surface constraint and an implementation decision.

  The live Codex dispatch interface available to Sage can select a model, reasoning effort, context fork, and task, but it cannot select a named custom-agent profile. Consequently, Sage encodes Scout, Researcher, Writer, Verifier, and Successor
  as immutable briefs rather than claiming that a saved profile or tool allowlist was enforced.

  That is not a rejection of custom agents in principle. If a future Codex surface exposes a verifiable named-profile selector, Sage could add saved profiles with role-specific tools, preloaded skills, and sandboxes while retaining briefs as
  per-attempt contracts. The current approach loses some Claude parity—particularly enforceable tool restrictions and preloaded clean-code guidance. See sage/skills/sage/references/codex.md:7.
