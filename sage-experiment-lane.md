# Sage experiment lane — verdict and plan

Status: proposal. Written 2026-08-19 by a sage run, from the user's idea. Nothing in this doc changes sage behavior yet. The implementation plan is in section 7.

The idea under test, condensed from the user's request (the original wording is at `ideas.md:2-7`):

> Introduce "experiment" behavior for the sage. Beside the normal plan, the sage might dispatch additional agents with unscripted models — for example, Fable as an extra verifier, or Haiku or a lower-tier alt model (gpt 5.6 luna) as an extra verifier. This is to explore the capabilities of model usages and allocations, in search of valuable allocations that are never published by Anthropic or OpenAI or other AI companies. Real example: a colleague claimed that in one session, gpt 5.6 luna at max effort found 30 genuine problems in a plan written by Fable. One catch: the sage should not experiment on lowering the model tier of the orchestration agent (the sage successors). Same for the implementer agents — haiku or gpt 5.6 luna should not be used for them.

## 1. Verdict

**The core idea is valid. The design below makes it systematic: extra off-plan units on installed placements, paired and scored. One of the idea's named examples — luna at max effort as a verifier — overstates what a run can dispatch; that boundary is F1. The others (a Fable, sonnet, or haiku extra verifier) are dispatchable today.**

**Corrections from the user (2026-08-19, after this doc's first review round):**

1. "Unscripted" means **off-plan** — units the traditional plan did not script — not models outside the installed roster. The user's example: the plan scripts one opus verifier; the experiment adds a sonnet verifier. The design already is this, so F1 now states the roster boundary instead of refuting the idea, and the example became hypothesis H6 in the backlog.
2. "Never published" means exactly the narrow gap this doc identified: vendors publish only the allocations they have confirmed as optimal, never the good-but-unconfirmed or unknown ones. C2 is therefore valid as intended.
3. The anecdote was an example, not evidence. C3's treatment — hypothesis H1 — stands with the user's agreement.

Split into four claims:

| # | Claim | Verdict |
| --- | --- | --- |
| C1 | Sage should sometimes dispatch extra agents on non-default allocations, to learn which allocations pay | **Valid.** Sage already has the recording half of this loop (memory bands, rules, promotion), and nothing forbids a hand-built paired trial today — this run ran one (section 4.3). What sage lacks is the systematic half: nothing selects an allocation hypothesis, funds it, bounds it, or records it comparably, run over run. This doc adds that half and nothing else. |
| C2 | The space worth exploring includes allocations no vendor publishes | **Valid as intended** (user correction 2, above). Two readings, two verdicts: the blanket reading — nothing about model allocation is published — is false, and section 4.2's verdict phrase ("false as a blanket claim") refutes exactly that reading; the user's intended narrow reading is supported by the same evidence: vendors publish only what they have confirmed as optimal, so seat-level playbooks, plan-level weak-catches-strong results, cross-family verification guidance — and everything contingent on local config, briefing style, and prices — stay unpublished. The lane targets that remainder. |
| C3 | The colleague's anecdote (luna, max effort, 30 genuine problems in a Fable plan) is evidence for C1 | **Treated as a hypothesis, with the user's agreement** (correction 3, above: it was an example, not evidence). The confounds in section 3, F2 are why an example cannot be more than a hypothesis. It is H1 in the backlog, and this run executed a small paired pilot of it (section 4.3). |
| C4 | Exclusions: never lower the orchestrator tier; never use haiku/luna-class models as implementers | **Valid, and extended.** The reshaped rule is stronger and simpler: experiments attach to reader seats only. No writer seat, no orchestrator seat, no parent seat, in either direction — not only "no lowering". See section 5.4. |

The one-sentence reshape: **an experiment is one additive, read-only, budget-capped, paired unit that tests a pre-registered allocation hypothesis and is scored by the run's own triage — never a substitute for a planned unit, and never a seat that can corrupt the deliverable.**

## 2. Why the goal is right

Three facts from this machine's own run log support C1 and C2.

1. The most load-bearing allocation rules sage runs on were discovered locally, not published. "The standard-tier checker has been right against the frontier one" is an established rule in skill text. "Apex stays out of the checker seat" is a placement rule in `sage-claude/references/harness.md`. Both came from local runs and local pricing. No vendor doc states either.
2. The alt lane's value was established by a deliberate local measurement. The 2026-08-18 smoke test run dispatched all three alt agents as no-op identity probes, confirmed the models from `message.model`, and measured boot floors per family. That run *was* an allocation experiment. It was user-directed. The lane proposed here makes that kind of measurement routine and cheap instead of occasional and hand-built.
3. The memory system is already an allocation-learning instrument, but a passive one. Bands and rules accumulate only what runs happen to hit. Discoveries arrive by accident (a mispriced refuter widens a band) or by user-directed research runs (the 2026-08-19 model-lineup run). A hypothesis with no run that happens to test it stays untested unless a user hand-builds a research run around it. The experiment lane closes that loop: it selects, funds, and records the variation the memory system was built to capture.

## 3. The fight — where the idea as stated is wrong

**F1. In-run, the experiment space is the installed placement space — "unscripted" means off-plan, not off-roster.** (Off-roster expansion exists in the design too, but only as user-executed proposals — the roster loop below.) The user confirmed this reading (section 1, correction 1): an experiment adds a unit the plan did not script, such as a sonnet verifier beside the planned opus one — and that example is fully dispatchable today (a plain dispatch, `model: sonnet`, effort recorded `(no control)`; it is H6 in the backlog). So is a haiku extra verifier. The boundary still matters, because the dispatchable space is fixed when a session starts. It is: the in-family models the Agent tool accepts (`haiku`, `sonnet`, `opus`, `fable`) — with no effort control on a plain dispatch; the four saved worker agents, each pinning model, effort, and tools (the fifth saved agent, `orchestrator`, pins no model — it inherits the parent and is never a plan unit); and the installed alt agents, each pinned to one configured outside-family model and dispatched with no `model` parameter. The anecdote's configuration — luna as a max-effort verifier — is not dispatchable on this machine. Luna is bound to `explorer-alt`: low effort, `Read`/`Glob`/`Grep` only, no shell. Reaching the anecdote's configuration needs a config edit, a re-run of `install.sh`, and a new session. Those are user actions. A run that edits user config to widen its own experiment space has made a persistent change to every future run without asking — that is rail territory, and the lane must never do it. Consequence for the design: the lane has two loops. The in-run loop experiments over the *installed* placement space. The roster loop *proposes* new installable placements as hint lines, and the user executes them.

**F2. The anecdote proves almost nothing — and the design must fix all three of its flaws.** (The user has since confirmed it was offered as an example, not as evidence; the flaws below are why the design treats every such example the same way.)
   - *No baseline.* "A fresh extra lens found problems" is already an established result. Disjoint mandates produce disjoint find-sets (established rule; logged multi-lens runs return near-zero duplicate findings, and the rare finding two lenses build independently counts as stronger evidence, not as overlap). A refuter aimed at a parent's own work has paid on every dispatch logged — 16 confirmations recorded to date, steered re-verdicts included. So an extra critic finding 30 problems is the expected outcome of *adding any critic*, on any model. The marginal claim — that *luna specifically* was a good buy at that seat — is only testable against a paired baseline: the same mandate, on the same frozen artifact, on the model the plan would have used, at a comparable cap. Anthropic's own engineering blog adds a second reason single-run comparisons mislead: identical starting points produce different valid trajectories, so one run's difference can be noise (section 4.2). The lane's pairing rule (section 5.2) and its count-before-promotion discipline (section 5.6) exist because of this flaw.
   - *"Genuine" is a triage output, not a reviewer's self-count.* Reviewers report what you ask them to look for; a finding count is inflatable and severity-blind. Sage already has the correct instrument: triage every finding into accepted / rejected-with-evidence / deferred / user-decision, on evidence. The lane's score (section 5.3) counts unique *accepted* findings per token, never raw findings.
   - *Effort attribution.* Reasoning effort has exactly one lever in this harness: `effort` frontmatter in a saved agent file. A plain dispatch has none. Whatever "max effort" meant in the colleague's session, the claim does not transfer to a placement that is not installed here — and an effort claim never transfers to a plain dispatch, which has no effort lever at all. Experiments record the effort level that was actually controlled, or `(no control)`, exactly as ledger rules already require.

**F3. Un-gated experimentation contradicts sage's own axioms.** "Not smarter than its model — better spent" and "never fan out to look busy" both cut against padding runs with exploratory dispatches. Worse, the budget rail is a multiplier on the run's own estimate, so a plan that adds experiment rows raises its own ceiling. The local watch list already flags this failure shape: "the 4× budget multiplier may be consumed rather than used." The design therefore funds experiments from measured headroom, caps them separately and low, limits them to one per run, and makes skipping them the default under any pressure (section 5.1).

**F4. Experiment results must not self-promote.** A one-run result is a `provisional` observation, not a rule. The memory protocol already handles this exactly: watch-list rows with counts, promotion only through `/sage-promote` on the user's word, falsifiers on every rule. The lane plugs into that pipeline and adds no new authority (it does add one detector — §5.6). A run never edits agent files, the tier table, or skill text because an experiment "worked".

**F5. The user's exclusions are right but under-specified, and one reframe makes them enforceable.** The user excluded *lowering* the orchestrator tier and *cheap models* as implementers. The reshaped rule is: **experiments attach to reader seats only** — verifier, reviewer, critic, explorer, researcher. Writer seats, the orchestrator/successor seat, and the parent seat are out of scope in both directions, up-tier and down-tier. Reasons per seat, in section 5.4. This is stronger than the user's version and simpler to enforce: sage already classifies every unit reader or writer at Step 1, so the gate is one check against an existing field.

**F6. Scoring is only strong at some seats.** Checker seats have a natural score: findings flow into triage, acceptance is evidence-backed, cost is readable from the transcript. Explorer and researcher seats score weakly — "coverage" has no cheap ground truth without paying for a redundant baseline. So v1 restricts hypotheses to checker-shaped seats (verifier, reviewer, critic), which is also where the anecdote points and where the corpus's open allocation questions live.

A read-only scout swept this repo's recommendation and research docs. Findings, with pointers:

### 4.2 Published research and vendor guidance (web report)

A web-research unit fetched primary sources on 2026-08-19. Confidence markers matter here: one source was fetched in full; the rest were confirmed at search-snippet level only, with arXiv IDs recorded for later verification. Per the standing rule, a snippet-level claim is a lead, not ground truth.

**Fetched in full — Anthropic, "How we built our multi-agent research system":** exactly one concrete role pairing is published — Claude Opus 4 as lead agent with Claude Sonnet 4 subagents outperformed single-agent Opus 4 by 90.2% on their internal eval. The verifier and judge seats are left unnamed. Nothing recommends a cheaper or outside-family model at a verification seat. The post also warns that identical starting points produce different valid trajectories, which is a direct argument against single-run allocation comparisons — the colleague's anecdote included.

**Published at snippet-level confidence (IDs recorded):**

- Learned routing and cascades are established methodology: RouteLLM (arXiv 2406.18665) trains a router on preference data against a cost-quality frontier (~95% of strong-model quality at 14–26% of strong-model calls); FrugalGPT (arXiv 2305.05176) formalizes cascades with a confidence stop (up to 98% cost cut at matched accuracy); Mixture-of-Agents (arXiv 2406.04692) layers aggregation.
- Weak-critic results exist in both directions. For: OpenAI's CriticGPT catches more inserted code bugs than paid human reviewers (same-tier critic, not cheap); weak-to-strong generalization (OpenAI, 2023) shows a weak supervisor eliciting much of a strong model's capability; "Weak Critics Make Strong Learners" (arXiv 2606.00424) reports a weaker model, used only as critic, lifting a stronger model's AIME pass@1 from 71.67 to 75.00. Against: at least one bug-discovery study found small models underperform as bug-finders even with more context. The outcome of H1-shaped hypotheses is genuinely open — which is what makes them experiments rather than assumptions.
- Self-preference and family bias in LLM judges is well documented by independent researchers (e.g., arXiv 2410.21819), yet no vendor guidance recommends cross-family verification because of it.

**Verdict on the premise:** "valuable allocations are never published" is false as a blanket claim. The defensible narrow version: nobody publishes (a) a vendor-endorsed seat-level playbook mapping roles to models, (b) a systematic study of a cheap or outside-family model finding many genuine problems in a frontier model's *plan* (code-level critique studies exist; plan-level ones were not found), or (c) vendor-endorsed cross-family verification guidance. Those three gaps, plus everything contingent on local config and prices, are the lane's target. The published methodology worth stealing: paired comparison on preference-style data, cost-quality frontiers, and the documented pitfall list — judge bias, single-run noise — which maps one-to-one onto this design's guards.

### 4.3 Pilot run inside this verification (n=1, provisional)

This run executed the smallest honest version of hypothesis H1, in the twin mode section 5.2 defines. The frozen draft of this doc — written by a Fable parent — was reviewed in parallel by two planned checkers on disjoint mandates (an `opus` verifier on grounding + spec, a `gpt-5.6-sol` verifier-alt on methodology) and by one additive experimental unit: `explorer-alt` on `gpt-5.6-luna` at low effort, carrying the `opus` verifier's mandate verbatim (the twin), with one tool-forced drop recorded — the luna unit has no shell, so it verifies by reading and grepping rather than by running commands. Neither twin saw the other's report. Scoring: unique accepted findings per unit after parent triage on evidence, and cost read from each transcript.

**Result — trial 1 of H1: unfavorable.** Identity was measured, not assumed: the experimental unit ran on `gpt-5.6-luna` (`message.model` in its own transcript); the cross-family methodology reviewer self-reported `OpenAI gpt-5.6-sol`. Costs from transcripts: luna twin 47k tokens in 31 seconds; opus twin 143k tokens in ~10 minutes. The luna unit's completion notification again read 0 tokens — the 5th local confirmation of that counter behavior.

Find-sets after triage: the opus twin returned 12 accepted findings (5 major) plus a refutation of this doc's own central wording — all accepted, all fixed in the round that followed. The luna twin returned 1 finding: the same root cause as the opus twin's sharpest catch (the Kind-vocabulary mislocation), independently constructed — which upgraded that finding, exactly as the shared-finding rule predicts. But it produced zero findings unique to it, and it confirmed as sound two claims the opus twin refuted (the "16 dispatches" figure and the absolute zero-duplicates phrasing). Per the pre-registered outcome rule: no unique accepted major-or-above finding from the experimental bundle → unfavorable.

Read against the anecdote: under a proper pairing, the cheap outside-family bundle did not out-find the frontier verifier at this seat on this artifact. It found one-twelfth the accepted findings at one-third the cost, produced no unique plan-breaking defect — its one catch, though real, was shared — and added two wrong confirmations. One trial decides nothing — the stated limits hold (n=1, low effort against the anecdote's claimed max, no shell, single trajectory, parent-as-judge). But it is exactly the kind of datum the anecdote is not: paired, triaged, costed, and recorded with its limits.

One more observation from the same wave, outside the pilot's scoring: the sol methodology refuter, on its disjoint mandate, returned 9 findings, exactly one of which — the gate's named instrument could not produce the figure it tests — was also built by the opus twin, independently, which upgraded it; the other 8 were invisible to the grounding mandate, the disjoint-mandates rule holding again.

Limits of the pilot, stated up front: n=1; the luna unit runs at low effort with read-only tools, not the anecdote's claimed max effort; the parent triaging is the same model that wrote the draft, and it knows which unit found what. These limits are the reason the result lands as a `provisional` watch-list row and nothing more.

## 5. Design — the experiment lane, v1

Vocabulary first. An **experiment** is one additive read-only unit, paired with one planned unit, that tests a named **hypothesis**: a (seat × installed bundle) allocation with a pre-registered prediction, score, and falsifier — where a **bundle** is everything a dispatch actually fixes at once: model, effort setting, tool scope, window. **Additive** means the plan is complete and correct without it: no planned unit is removed, resized, or re-scoped to make room.

### 5.1 The gate — when a run may carry an experiment

All of these must hold, checked at Step 2 (plan time) and re-checked at the experiment's dispatch point:

1. Risk is medium or high — so a triage stream exists to score against.
2. The plan already carries a checker seat whose mandate the experiment can twin (section 5.2).
3. Headroom is measured, not hoped for. Headroom = core estimate − (landed actuals from per-unit `--status` spend + the remaining estimates of every in-flight row + the parent's own projected spend, counted by the spend convention, never by occupancy). The experiment dispatches only if headroom ≥ its allowance. `--status` alone cannot produce this figure — it carries no parent spend — so the projection is the parent's own, the same arithmetic the budget rail already runs.
4. Experiment allowance = min(the twin row's own estimate, 10% of the core estimate). The core estimate excludes the experiment line, and the rail-4 ceiling is computed as 4 × core + 1 × allowance — the experiment allowance is never multiplied, so an 80k experiment adds 80k of ceiling, not 320k. The allowance binds at dispatch — an experiment row estimated above it never launches — and is accounted afterwards: an overrun observed at the next `--status` read is recorded as an unfavorable cost datum and counts toward the lane's retirement conditions (5.6). No mid-flight token stop exists in this harness, and the design claims none. This changes the whole-task ceiling formula for runs that carry an experiment line, so it is a `## Rails` edit, and the implementation plan allocates it.
5. At most one experiment per run.
6. The seat is a reader seat, and the experimental unit is never the sole checker of anything (section 5.4).
7. An alt-agent experiment passes no `model` parameter. An in-family plain-dispatch experiment names its model and records effort as `(no control)`.

Any gate failing → no experiment, no second thought, one ledger line: `experiment: skipped (<gate>)`. Skipping is the default under pressure. A knob in SKILL.md's Defaults table turns the lane off entirely.

One consequence of gate 4, stated rather than hidden: a hypothesis whose twin sits in an expensive band — an adversarial refuter on a multi-claim mandate runs 375–800k on this machine — is not dispatchable in an ordinary-sized run, because no ordinary 10% line covers its twin's estimate. H2 in the backlog carries this constraint explicitly. Raising the allowance for one run is a user decision, never the lane's.

### 5.2 The pairing rule — twin mode

An experiment is scoreable only against a baseline. V1 supports exactly one shape:

- Pick a planned checker row (the **twin**). The experimental unit gets the twin's mandate text verbatim, the same frozen artifact, and the same return format — adjusted only where the experimental agent's tools force it, and every adjustment is recorded in the trial record. No unregistered mandate difference may remain.
- Both run on the same freeze. Neither sees the other's report.
- The experimental unit's findings enter triage like any other unit's — as claims from an unprivileged source, on evidence.

**The estimand is the installed bundle, not the model.** A dispatch fixes model, effort, tools, and window together, and the bundle is all sage can ever choose between — so the bundle is what a trial compares. The trial record lists every factor that differed between twin and experiment (model, effort, tools, mandate drops), and a result is a claim about that bundle at that seat, never about the model in isolation. A tool-forced drop is part of the bundle being measured: a no-shell critic that skips the command checks is measuring the no-shell bundle, and the record says so.

Twin mode deliberately dispatches a second unit on the *same* mandate — exactly the shape the standing rule discounts ("a second reviewer on the same mandate buys redundancy"). The lane claims an exemption and names what it buys instead: comparability. The implementing edit writes this exemption next to that rule in SKILL.md, so the two never silently conflict.

Why twin mode only: it is the only shape where "which bundle was the better buy at this seat" is answerable from one run. Ablations (removing a planned unit to see what breaks) violate additivity. Solo probes (an experiment with no twin) reproduce flaw F2-i.

### 5.3 Scoring

Before scoring, merge both find-sets and dedupe by root cause — the standing triage rule — and where the run allows it, rule on the merged, attribution-stripped list first and attach attribution after. Then compute per unit (twin and experiment):

- accepted findings unique to this unit, **counted per severity** — blocker, major, minor stay separate. Five accepted minors never outweigh one accepted blocker, and no single scalar is ever computed;
- accepted findings shared with the other (a finding both units built independently counts for both, and upgrades the finding itself);
- rejected findings, and any confirmation the other unit refuted;
- token cost, read from the unit's transcript — never from the completion notification, which reads zero on alt-lane units (5 local confirmations) — plus the parent triage cost the experimental unit's report added.

Trial outcome, one of three, pre-registered here. Evaluate in order; the first clause that matches decides. (1) **null** — neither unit produced a unique accepted major-or-above finding. (2) **favorable** — the experimental unit produced at least one unique accepted major-or-above finding at lower cost per such finding than the twin (cost = transcript spend + attributed triage cost), or its accepted set equals the twin's at no more than half the twin's cost. (3) **unfavorable** — everything else. Every scored trial updates the hypothesis row: outcome, date, one-line score, and a pointer to the run's ledger. There is no unrecorded trial. The registry row stores derived one-line outcomes and pointers only; raw dispositions and costs stay in the run's ledger and transcripts, never copied.

Two recorded limits travel with every score. The gate samples only healthy runs with measured headroom, so results generalize to runs with headroom, not to runs under pressure. And the parent-as-judge bias — the triaging parent knows which unit found what, and may have authored the artifact — is recorded in the row the first time each hypothesis is scored.

Anti-Goodhart guard: the score counts findings *accepted on evidence*, and acceptance disputes settle with a command where one exists — both already standing rules. A hypothesis must not be scored by raw finding count, reviewer confidence, or report length.

Single-run noise guard: one paired run is still one trajectory, and identical starting points produce different valid trajectories (Anthropic's own multi-agent post, section 4.2). That is why a score is one confirmation, never a conclusion — promotion needs three, on the standard trigger.

### 5.4 Seats — what may and may not be experimented on

| Seat | Experiments? | Why |
| --- | --- | --- |
| Verifier / reviewer / critic (reader) | **Yes — v1's whole scope** | Natural score via triage; a wrong output is just a rejected claim; the anecdote and the corpus's open questions (apex-as-checker, cheap-alt-as-critic) live here |
| Explorer / researcher (reader) | Not in v1 | Weak scoring (F6); revisit after v1 produces promoted rows |
| Implementer / any writer | **Never** | Mutates trees; failure costs fix rounds and lease churn; confounds the deliverable itself; the failure ladder already owns writer-tier escalation. This covers and extends the user's implementer exclusion — in both directions |
| Orchestrator / successor | **Never** | Inherits the parent by design (no `model:` line); owns run state; failure is unrecoverable by cheap retry; no counterfactual exists to score against. The user's exclusion, kept verbatim |
| Parent | **Never** | Same reasons as orchestrator; also the triage judge — experimenting on the judge invalidates the score |
| Sole checker of a high-stakes claim | **Never as replacement** | Experiments are additive; the planned checker always runs. An experimental refuter is an extra voice, triaged as data |

### 5.5 The hypothesis registry

Hypotheses live in `memory/local.md`'s Watch list as rows of Kind `experiment`. The Kind vocabulary is defined in the seed file's preamble (`sage-claude/memory/local-seed.md`), not in `references/memory.md` — and an installed `local.md` is append-only user data. So the implementing edit updates the seed for new installs and adds one protocol sentence to `references/memory.md` naming the new Kind; existing machines simply start appending rows that use it. Nothing breaks: the structural invariant check reads table headers, never Kind values (confirmed against the invariants section, and independently by two reviewers of this doc). One row per hypothesis, its Observation cell carrying: the seat, the twin bundle, the experimental bundle, the artifact-class stratum, the prediction, and the running score line — trials / favorable / null / unfavorable, latest ledger pointer. V1 defines exactly two artifact classes — `prose/plan corpus` (plans, docs, skill text) and `code diff`. A hypothesis declares one; anything else is out-of-stratum. Finer strata are a `/sage-promote` refinement, not a run's. Selection at plan time is deterministic and rotation-based: among hypotheses whose declared twin seat and stratum match this plan, pick the least-recently-trialed; tie → oldest row. Rotation, not highest-count-first — a count-greedy rule lets one early noisy result monopolize every later run. Hypotheses that matched but were not selected are named in the ledger's experiment line, so the eligible population stays auditable.

New hypotheses come from three sources only: the user; a run's own recorded anomalies (a watch-list lesson that names an allocation); and `/sage-promote` stage three when the model lineup changes. A run may append a hypothesis row. Only the user (via config + `install.sh`) can widen the installed roster the hypotheses draw from — the run's role in roster expansion is one hint line naming the proposal.

### 5.6 Promotion and retirement

Promotion needs **three favorable trials within the hypothesis's declared stratum** — same twin bundle, same experimental bundle, same artifact class. Trials outside the stratum are recorded but do not count toward the three: three easy artifacts must not promote a bundle that loses on hard ones, and a count is only honest when its members are comparable.

One honest correction this doc's own review forced: no existing hint trigger fires on a Watch-list row's count — the promotion triggers read the Rules table. So the lane adds **one new machine-checkable trigger row** to the hint table in `references/memory.md`: a Watch-list row of Kind `experiment` with favorable ≥ 3 in-stratum → one hint line. That is a new detector, and it is admitted as one. It is not new authority: the hint still only prints one line, and `/sage-promote`, on the user's word, still decides whether the tier table, an agent file, or skill text changes. A falsifier firing → retirement candidate, standard path.

**The lane's own falsifier, pre-registered here, with its observer named.** `/sage-promote` computes the lane counters from the registry rows when it runs: total scored trials is the sum of the rows' trials fields; reversals are readable where promotion actually lands them: a promoted allocation becomes a Rules-table row whose `Promoted` cell records retirement and re-promotion with dates; allowance overruns and wall-clock delays are readable from the run-log rows that recorded them. Retire the lane when any of these holds: ten scored trials produced zero promotion hints; a promoted allocation change was reversed twice; experiments exceeded their allowance or materially delayed the run, in three runs (read from the run-log rows that recorded them). Every condition is a count over fields this design requires to be written, so the falsifier is checkable rather than aspirational.

## 7. Implementation plan

Ordered, sized, each step falsifiable. Total new text across the corpus should stay under ~180 lines — the lane reuses existing machinery everywhere it can.

1. **`sage-claude/SKILL.md`** (~50 lines): one Defaults row (`Experiment lane | on — gate in Step 2; off = never dispatch experiments`); a short `### Experiments` clause in Step 2 (gate + registry selection + the non-multiplied budget line in the Plan block); one Step 5 sentence (experimental findings triage like any unit's) plus one sentence beside the disjoint-mandates rule naming twin mode as its recorded exemption (same mandate bought deliberately, for comparability); one Step 6 sentence (score → registry row update; roster proposals → hint line); one sentence in `## Rails`: a plan carrying an experiment line computes the whole-task ceiling as 4 × core + 1 × experiment allowance. Done when: a dry-read of Steps 1–6 shows exactly one dispatch path for experiments, and gate 3's arithmetic is reconstructible from the ledger plus the parent's own projection.
2. **`sage-claude/references/dispatch.md`** (~25 lines): Plan-table `E` flag on the experiment row; the experiment brief delta (twin mandate verbatim, tool-forced drops recorded); the score line's shape in Findings and Run record. Done when: the ledger shapes round-trip — a run record written from the shapes renders the experiment without free text.
3. **Memory protocol and seed** (~15 lines across two files): in `sage-claude/memory/local-seed.md`, the Watch-list preamble's Kind vocabulary sentence gains `experiment` — this is where the vocabulary actually lives, and new installs pick it up from the seed. In `sage-claude/references/memory.md`, one protocol sentence naming the new Kind, plus **one new trigger row** in the hint table: Watch-list row of Kind `experiment`, favorable ≥ 3 in-stratum → hint (the detector section 5.6 admits). Existing machines: an installed `local.md` is append-only user data and is never edited — its first `experiment` row simply uses the new Kind, which the structural invariant check does not read. Done when: `grep -n experiment sage-claude/memory/local-seed.md` returns the vocabulary line; the hint table carries the new row; the structural-invariants section still fixes only the sentinel, the section order, and the table headers.
4. **`sage-claude/references/harness.md`** (~10 lines): cross-reference only — the lane adds no harness mechanics; state that experiment dispatches obey the alt-lane no-param rule and the effort-lever facts as written. Done when: no new mechanism is described, only pointers.
5. **`claude-skills/sage-promote/SKILL.md`** (~8 lines): the lane counters live here — at promote time, compute total scored trials (sum of registry rows' trials fields), zero-hint history, reversals (Rules `Promoted` cells), and allowance overruns / delays (run-log rows), and evaluate the lane's three retirement conditions (5.6). Done when: each of the three conditions names the exact field it counts.
6. **Seed the registry** (~10 lines in `memory/local-seed.md` guidance, plus H1–H4 rows appended to this machine's `memory/local.md` watch list by the implementing run, under the normal append rules).
7. **Pilot phase**: run the lane on the next 3 medium+ runs; each scores one hypothesis. Then review via `/sage-promote`. Done when: 3 scored rows exist, or 3 `experiment: skipped (<gate>)` lines exist and the gate reasons are examined instead.
8. **Out of scope for the implementing run**: any edit to `~/.claude/subagents-alt-models.conf`, any new agent file, any `install.sh` change. Roster expansion — including a luna-class model at a verifier seat with shell and high effort, the configuration the anecdote actually claims — is a user decision, proposed by hint line. The genuine one-line action, if the user wants it: set `verifier-alt=gpt-5.6-luna[1m]` in the conf, re-run `install.sh`, start a new session. The verifier-alt template already carries `effort: high` and shell, so this reaches the anecdote's shape exactly. The tradeoff, stated plainly: it repoints the slot, so sol leaves the checker seat while luna holds it. Adding a second slot (`verifier-alt2`) is not a config line — it needs a new agent template and an installer change, both out of scope here.

Risks of implementing: (a) ritual spending if the gate erodes — mitigated by the lane's own pre-registered falsifier (5.6) and the Defaults off-switch; (b) score gaming by mandate drift between twin and experiment — mitigated by the verbatim-mandate rule and recording tool-forced drops; (c) memory bloat — one row per hypothesis, not per run; confirmations re-date the row.

## 8. Non-goals

- No autonomous model-roster changes. Ever.
- No experiments on writers, orchestrators, or the parent (5.4).
- No new authority: promotion stays with `/sage-promote`, on the user's word. One new *detector* is added (the hint trigger row in step 3) — it prints one line and decides nothing.
- No claim of statistical rigor: n accumulates across runs in the registry; single-run scores stay `provisional`. The lane buys cheap, honest, paired observations — not benchmarks.
- No replacement of the failure ladder: escalating a struggling unit one tier is the ladder's job, not an experiment.
